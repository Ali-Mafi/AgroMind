# AgroMind Progress — 2026-09-03

## Session Summary

This session focused on building the first complete Weather Center foundation for AgroMind using real farm coordinates and real Open-Meteo / Air Quality data.

The main goals were:

1. Expand the Weather domain beyond the small Dashboard summary.
2. Introduce a dedicated `/weather` page driven by the selected real farm.
3. Build reusable normalization and composition layers for current conditions, wind, dust, visual state, hourly forecast, and air quality.
4. Keep weather semantics truthful and avoid presenting forecast-model values as direct physical observations.
5. Experiment with dynamic weather backgrounds and identify the current CSS-only visual system as a temporary implementation that must be replaced by a more photorealistic asset-based system.

## 2. Expanded Open-Meteo Forecast Request

The weather service now requests the expanded current, hourly, and daily fields from Open-Meteo.

Explicit units are used:


Each state includes a day/night variant, for example:

# Air Quality and Dust

## 6. Air Quality Service

A new Air Quality service was added using Open-Meteo's Air Quality API.

Current and hourly data supports:

```text
PM10
PM2.5
dust
aerosol optical depth
European AQI
US AQI
```

Missing values are represented as `null`; they are never converted into fake zero values.

---

## 7. Air Quality Hook

A dedicated `useAirQuality` hook was added with the same lifecycle style as the Weather hook.

Behavior:

```text
No coordinates
→ no request

Loading
→ loading state

Success
→ real Air Quality data

Failure
→ Air Quality unavailable
```

Air Quality is supplementary and does not cause the Weather page itself to fail.

---

## 8. Dust Condition Resolver

A dust resolver was introduced to derive a visual dust state from real Air Quality data.

Possible states:

```text
unavailable
not-dusty
dusty
```

Dust intensity can be:

```text
light
moderate
heavy
```

The resolver uses dust share, PM10, and aerosol optical depth as a visual heuristic.

Important rule:

```text
Air Quality unavailable
≠
not dusty
```

The system does not invent a clean-air result when the underlying dust data is missing.

A `useWeatherCenter` composition hook now combines:

# Dedicated Weather Page

## 10. `/weather` Route

A dedicated Weather Center page was added:

```text
app/weather/page.tsx
```

The page is driven by real Farm context.

Behavior:

```text
No farms
→ Add Farm empty state

Farm exists but has no coordinates
→ Configure Location state

Weather loading
→ loading state

Weather request fails
→ Weather unavailable state

Valid farm coordinates + successful request
→ Current Weather Hero
```

The shared Farm Selector is used so switching the selected farm also changes the Weather data source.

No demo farm or fake operational weather values were introduced.

# Hourly Forecast

## 12. Hourly Forecast Component

A reusable Hourly Forecast component was added.

The current implementation uses the next 24 forecast records and displays per hour:

```text
time
weather icon
temperature
feels-like temperature
precipitation probability
wind direction
wind speed
```

The forecast starts from the current hour for the farm's own timezone rather than assuming the browser's local timezone.

The Hourly Forecast is currently integrated inside the Current Weather Hero so the Weather experience reads as one unified surface rather than a separate white card.

Horizontal scrolling / snap behavior is used for the hourly cards.

# Precipitation Semantics

## 13. Current Weather Time / Interval Metadata

Current weather now preserves provider timing metadata:

```text
time
intervalSeconds
```

This allows AgroMind to communicate what the precipitation value actually represents instead of presenting it as a direct rain-gauge observation.

---

## 14. Precipitation UI Clarified

The previous `Rain` card semantics were changed to `Precipitation`.

The Hero now distinguishes:

```text
precipitation amount
precipitation probability
model interval
```

Example presentation:

```text
PRECIPITATION
0.0 mm
0% chance
Model estimate · previous 15 min
```

This was introduced after testing a location where real-world rain conditions and Open-Meteo's model value did not perfectly agree.

Important product rule established:

```text
Forecast-model precipitation
≠
direct physical observation
```

For future production accuracy, current precipitation may eventually need an observation/radar source in addition to forecast-model data.

# Weather Accuracy Findings

## 15. Expected Provider Differences

Testing showed small differences between Apple Weather and AgroMind/Open-Meteo for values such as:

```text
temperature
feels-like temperature
wind
```

Small differences were treated as expected because providers may use different forecast models, grid resolutions, update times, and apparent-temperature calculations.

The project should not attempt to artificially force Open-Meteo values to match Apple Weather.

Exact farm coordinates remain the intended source location for AgroMind Weather.

---

# Dust / Visual-State Correction

## 16. Dust No Longer Replaces the Base Weather State

During testing, a clear night could become a fully brown `dust-night` background because dust was allowed to override the base weather state.

That behavior was changed conceptually so the base weather state remains independent:

```text
Mainly Clear + Night
→ clear-night
```

Dust remains separate in Weather Center data and should later become an atmospheric overlay rather than replacing the entire sky condition.

Target future model:

```text
Base weather
+
optional dust overlay
```

rather than:

```text
dust
→ replace base weather completely
```

# Dynamic Weather Background Experiment

## 17. CSS Weather Background Engine

A dynamic CSS Weather Background component was introduced to test weather-driven visual presentation.

It supports conditions such as:

```text
clear
partly cloudy
cloudy
rain
heavy rain
storm
snow
fog
```

and day/night variants.

The first implementation used layered gradients, clouds, rain, snow, fog, grain, and other animated atmospheric effects.

---

## 18. Performance Iteration

Testing showed that the heavier version of the CSS engine caused visible blur and page slowdown because of large animated / blurred layers and texture effects.

A lighter version was then introduced that removed or reduced expensive effects such as:

```text
large blur filters
SVG turbulence grain
heavy animated full-size layers
```

The current committed CSS background is therefore lighter than the first experiment.

---

## 19. CSS-Only Visual Direction Rejected as Final Design

Even after the performance cleanup, the background was still judged visually insufficient.

Examples observed during testing:

```text
clear night
→ mostly dark navy color / gradient

rain
→ mostly gray color / gradient
```

The result did not provide the realistic atmospheric depth expected for the final AgroMind Weather experience.

Decision:

```text
CSS-only photorealistic weather background
→ rejected as final direction
```

The current Weather Background should be treated as temporary / transitional implementation, not finished UI.

# Weather Background V2 Direction

The next Weather visual implementation should use:

```text
optimized photorealistic AVIF / WebP base assets
+
weather-aware color grading
+
very lightweight CSS motion overlays
```

Suggested initial asset states:

```text
clear-day
clear-night
partly-cloudy-day
partly-cloudy-night
cloudy-day
cloudy-night
rain-day
rain-night
storm-day
storm-night
snow-day
snow-night
fog-day
fog-night
```

Target properties:

```text
photorealistic
natural
consistent art direction
no cartoon look
no visible text
no fake landscape-dependent operational meaning
suitable behind white Weather UI
optimized for frontend performance
```

Only the currently active / selected weather background should need to load; the app should not load every forecast day's heavy visual asset simultaneously.
