# Irrigation Scheduling and Domain Work

## 1. Irrigation Schedule Lifecycle

The Irrigation page now derives schedule state from the current local time instead of keeping every existing schedule permanently marked as scheduled.

Lifecycle:

```text
Future schedule
→ scheduled

Schedule time reached or passed
→ past-due
```

The UI clock refreshes every minute so the schedule can transition without requiring a full page refresh.

A past-due schedule is not automatically treated as completed because AgroMind does not yet have hardware confirmation or manual completion confirmation.

---

## 2. Past-Due Rescheduling UX

Past-due schedules now have an explicit recovery flow instead of being silently removed.

The Irrigation Overview shows a warning and a `Reschedule Irrigation` action. The action scrolls the user back to the schedule form.

The scheduling section uses a stable DOM id:

```text
irrigation-schedule-{farmId}
```

Flow:

```text
Past-due schedule
→ warning
→ Reschedule Irrigation
→ smooth scroll to scheduling form
→ user selects a new future date/time
```

---

## 3. Schedule Status Typing Fixed

The schedule status domain type is:

```ts
export type IrrigationScheduleStatus =
  | "scheduled"
  | "past-due";
```

The previously discovered mismatch between display-style values and machine-readable values was fixed.

`IrrigationOverview.status` now uses `IrrigationScheduleStatus` instead of a generic `string`.

The Irrigation page now emits:

```text
scheduled
past-due
```

The presentation component converts those values into user-facing labels:

```text
scheduled → Scheduled
past-due → Past due
```

This makes the Past Due branch type-safe and prevents casing/value mismatches.

## 4. Timezone-Aware Schedule Metadata

Irrigation schedules support:

```ts
timeZone?: string;
```

The timezone is resolved when a schedule is saved using:

```text
Intl.DateTimeFormat().resolvedOptions().timeZone
```

This prepares schedules for a future backend scheduler where local wall-clock values such as `06:30` must be interpreted in the correct timezone.

---

## 5. Stable Schedule Identity and Audit Metadata

Schedules now support:

```ts
id?: string;
createdAt?: string;
updatedAt?: string;
```

Behavior:

```text
New schedule
→ new UUID
→ createdAt created
→ updatedAt created

Edit / reschedule
→ same schedule id
→ createdAt preserved
→ updatedAt refreshed
```

These fields prepare schedules for future event correlation and audit history.

---

## 6. Schedule Revisions

Schedules now support:

```ts
revision?: number;
```

Behavior:

```text
New schedule
→ revision 1

First reschedule
→ revision 2

Next reschedule
→ revision 3
```

The logical schedule id remains stable while the revision changes.

This prevents future idempotency logic from confusing an old execution with a newly rescheduled execution.

Example:

```text
schedule abc / revision 1
→ original execution

schedule abc / revision 2
→ rescheduled execution
```

## 7. Controller Status Moved Into Domain Types

Controller status is now a reusable domain type:

```text

offline

```

This allows the same state model to be shared by UI, scheduler logic, backend services, and future hardware integration.

## 8. Irrigation Execution Routes

Execution routes were introduced:

```text
manual
automatic
unavailable
```

Resolver:

```text
not-connected → manual
connected     → automatic
offline       → unavailable
error         → unavailable
```

An offline/error controller does not silently fall back to manual mode because the user may be expecting automation and must instead receive a truthful failure/warning state.

---

## 9. Irrigation Due Actions

Execution routes are mapped to due actions:

```text
manual
→ send-manual-reminder

automatic
→ request-automatic-start

unavailable
→ report-controller-unavailable
```

A combined resolver returns both the execution route and the due action while remaining side-effect free.

## 10. Irrigation Event Model

A typed event model exists in:

```text
features/irrigation/types/irrigation-events.ts
```

Events modeled:

```text
schedule_due
manual_reminder_sent
automatic_start_requested
controller_unavailable
irrigation_started
irrigation_failed
irrigation_completed
```

Every event carries:

```text
id
farmId
scheduleId
scheduleRevision
occurredAt
```

Important semantic rule:

```text
automatic_start_requested
≠
irrigation_started
```

A start request only means AgroMind requested an action. `irrigation_started` must only be recorded after real device evidence confirms irrigation has physically started.

It standardizes event identity/timestamps and supports injected dependencies such as:

## 12. Due Idempotency Key

A deterministic due key generator was added:

```text
features/irrigation/lib/create-irrigation-due-key.ts
```

Format:

```text
irrigation:{farmId}:{scheduleId}:revision-{revision}:schedule-due
```

A rescheduled execution gets a different key because its revision changes.

The helper only defines identity. Real duplicate prevention will still require an atomic backend/database claim.

---

## 13. Due Plan Resolver

A due-plan resolver was added:

```text
features/irrigation/lib/resolve-irrigation-due-plan.ts
```

A valid plan contains:

```text
farmId
scheduleId
scheduleRevision
duration
controllerStatus
route
action
idempotencyKey
```

Legacy schedules without a reliable id or revision are rejected instead of receiving invented identities.

Possible invalid reasons:

```text
missing-schedule-id
missing-schedule-revision
```

This is intentionally fail-safe because future automation will control physical hardware.

# Safe Automation Contracts Prepared for Future Backend

## 14. Atomic Due Claim Contract

A new domain contract was added:

```text
features/irrigation/types/irrigation-idempotency.ts
```

Claim request identity includes:

```text
idempotencyKey
farmId
scheduleId
scheduleRevision
workerId
requestedAt
```

Claim results:

```text
claimed
already-claimed
already-completed
```

A claim also contains a lease expiration time so a crashed worker does not permanently lock an irrigation schedule.

---

## 15. Claim Completion / Failure Lifecycle

The claim contract now also models how a worker finishes an attempt.

Completion/failure resolution states include:

```text
completed
failed
lease-lost
claim-not-owned
```

Failure dispositions:

```text
retry-after-lease
manual-review
do-not-retry
```

`manual-review` is important for ambiguous hardware situations where retrying a physical command may be unsafe.

Example:

```text
Start command sent
→ network response lost
→ device state unknown
→ manual-review
```

---

## 16. Controller Command Contract

A controller command domain model was added:

```text
features/irrigation/types/irrigation-controller-command.ts
```

The current logical command is:

```text
start-irrigation
```

Command identity includes:

```text
commandId
idempotencyKey
controllerId
farmId
scheduleId
scheduleRevision
duration
requestedAt
```

Dispatch results:

```text
accepted
already-accepted
rejected
unknown
```

Important rule:

```text
accepted
≠
irrigation_started
```

`accepted` only means the gateway/controller layer accepted the logical command.

---

## 17. Controller Command Idempotency Key

A deterministic command key generator was added:

```text
features/irrigation/lib/create-irrigation-controller-command-key.ts
```

Format:

```text
irrigation:controller:{controllerId}:farm:{farmId}:schedule:{scheduleId}:revision-{revision}:start-irrigation
```

Retries of the same logical command must reuse the same key.

A changed schedule revision or changed controller creates a different logical command identity.

---

## 18. Deterministic Start Command Factory

A factory was added:

```text
features/irrigation/lib/create-irrigation-controller-start-command.ts
```

The factory derives a stable `commandId` from the deterministic command key instead of generating a new random id on every retry.

Rule:

```text
same controller
+ same farm
+ same schedule
+ same revision
→ same logical command identity
```

`requestedAt` is passed into the factory rather than generated internally so retrying a stored logical command does not masquerade as creating a new command.

---

## 19. Controller Command Attempt Model

Network attempts were separated from the logical command in:

```text
features/irrigation/types/irrigation-controller-command-attempt.ts
```

Each attempt has:

```text
attemptId
commandId
attemptNumber
startedAt
finishedAt?
outcome?
reason?
```

Attempt outcomes:

```text
accepted
already-accepted
rejected
unknown
```

This allows multiple network attempts to belong to one logical command without creating multiple physical command identities.

Example:

```text
Logical command X
├── attempt 1 → unknown / timeout
└── attempt 2 → already-accepted
```

A device confirmation model was added:

```text
features/irrigation/types/irrigation-device-confirmation.ts
```

Valid start evidence currently includes:

```text
controller-state: irrigating

```

The confirmation is correlated to:

Target sequence:

```text
→ real device confirmation
→ irrigation_started
```

# Product Direction Decision

During this session the project direction was changed intentionally.

Backend, scheduler, notification, and hardware implementation are now **paused**.

The next priority is to finish the AgroMind frontend as a complete product surface first.

Target order:

```text
PHASE 1 — Frontend Complete
        ↓
PHASE 2 — Backend Foundation
        ↓
PHASE 3 — Real Data Integration
        ↓
PHASE 4 — Notifications / Automation
        ↓
PHASE 5 — Hardware Integration
        ↓
PHASE 6 — Production Hardening
```

Reasoning:

- Finish product UX and all required states before fixing backend API contracts permanently.
- Avoid repeatedly switching between frontend and backend work.
- Let the final frontend define exactly what data/API surfaces the backend must provide.
- Keep real-app pages truthful while backend services are missing.

Core UI rule remains:

```text
Source not connected
→ Not connected

Source connected but no reading
→ No data

Real source available
→ real value

Failure
→ error / unavailable
```

Fake operational values remain forbidden outside the Landing page.
