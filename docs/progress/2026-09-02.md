# AgroMind Progress — 2026-09-02

## Session Summary

This session focused on preparing AgroMind's irrigation scheduling architecture for reliable future automation without introducing fake client-side execution, fake notifications, or simulated hardware behavior.

The work in this session prepares the domain model and scheduling contracts that will later be used by a real backend scheduler, notification system, and irrigation controller integration.

---

## 1. Irrigation Schedule Lifecycle

The Irrigation page was updated so an existing schedule can transition based on the current local time instead of remaining permanently labeled as scheduled.

The page now calculates the schedule timestamp from the stored local date and time and refreshes the current time every minute.

Intended lifecycle:

```text
Future schedule
→ scheduled

Schedule time reached or passed
→ past-due
```

The schedule is not automatically marked completed because AgroMind does not yet have hardware confirmation or manual completion confirmation.

---

## 2. Past-Due Rescheduling UX

Past-due schedules were given a dedicated recovery path instead of being silently removed.

The Irrigation Overview now supports a reschedule action that scrolls the user back to the irrigation scheduling form.

The scheduling section receives a stable DOM id:

```text
irrigation-schedule-{farmId}
```

The intended UX is:

```text
Past-due schedule
→ warning shown
→ Reschedule Irrigation
→ smooth scroll to schedule form
```

The existing schedule remains visible until the user chooses a new future date and time.

---

## 3. Schedule Status Domain Preparation

A domain status type was introduced:

```ts
export type IrrigationScheduleStatus =
  | "scheduled"
  | "past-due";
```

This is intended to separate machine-readable application state from user-facing labels such as:

```text
Scheduled
Past due
```

A follow-up issue was discovered during the repository review and is documented in the Known Issues section below.

---

## 4. Timezone-Aware Schedule Metadata

Irrigation schedules were extended with timezone information.

New schedules can now store:

```ts
timeZone?: string;
```

The timezone is resolved from the user's environment when a schedule is saved:

```text
Intl.DateTimeFormat().resolvedOptions().timeZone
```

This prepares schedules for a backend scheduler where a value such as `06:30` must be interpreted in the correct timezone.

Legacy schedules remain compatible because the timezone field is optional.

---

## 5. Stable Schedule Identity

Schedules now support a persistent identifier:

```ts
id?: string;
```

New schedules receive a UUID.

When an existing schedule is rescheduled, the same schedule id is preserved instead of generating a new identity.

This will allow future irrigation events, backend jobs, and controller commands to be correlated with the correct schedule.

---

## 6. Schedule Audit Timestamps

Schedules now support:

```ts
createdAt?: string;
updatedAt?: string;
```

Behavior:

```text
New schedule
→ createdAt created
→ updatedAt created

Reschedule / Edit
→ createdAt preserved
→ updatedAt refreshed
```

These timestamps use ISO UTC timestamps because they represent system audit time rather than the user's scheduled local irrigation time.

---

## 7. Schedule Revisions

A revision number was added to distinguish multiple versions of the same logical schedule:

```ts
revision?: number;
```

Behavior:

```text
New schedule
→ revision 1

First reschedule
→ revision 2

Next reschedule
→ revision 3
```

The schedule id remains stable while the revision changes.

This prevents future idempotency logic from confusing an old execution with a newly rescheduled execution.

Example:

```text
schedule abc / revision 1
→ first planned execution

schedule abc / revision 2
→ rescheduled execution
```

## 8. Controller Status Moved Into Domain Types

The irrigation controller status type was moved out of the UI component and into the irrigation domain types.

Supported controller states:

```text
not-connected
connected
offline
error
```

This allows the same status model to be reused by UI, scheduler logic, backend integration, and future hardware services.

## 9. Irrigation Execution Routes

A domain-level execution route was introduced:

```text
manual
automatic
unavailable
```

Resolver:

```text
not-connected
→ manual

connected
→ automatic

offline
→ unavailable

error
→ unavailable
```

An offline or error controller is intentionally not silently converted into manual irrigation because that could hide a failed automation expectation from the user.

---

## 10. Irrigation Due Actions

A second resolver maps execution routes into concrete due actions:

```text
manual
→ send-manual-reminder

automatic
→ request-automatic-start

unavailable
→ report-controller-unavailable
```

This separates the decision about the execution route from the action the scheduler must request.

## 11. Combined Due Decision Resolver

A combined domain resolver now returns both:

```text
route
action
```

Example:

```text
controllerStatus = not-connected
→ route = manual
→ action = send-manual-reminder
```

Example:

```text
controllerStatus = connected
→ route = automatic
→ action = request-automatic-start
```

The resolver remains side-effect free.

## 12. Irrigation Event Model

A typed irrigation event model was introduced in:

```text
features/irrigation/types/irrigation-events.ts
```

Events currently modeled:

```text
schedule_due
manual_reminder_sent
automatic_start_requested
controller_unavailable
irrigation_started
irrigation_failed
irrigation_completed
```

Every event contains common identity data:

```text
id
farmId
scheduleId
scheduleRevision
occurredAt
```

This allows events to be correlated to an exact farm, schedule, and schedule revision.

Important semantic separation:

```text
automatic_start_requested
≠
irrigation_started
```

A start request means AgroMind requested the action.

`irrigation_started` must only be recorded after real controller confirmation.

## 13. Irrigation Event Factory

A standardized event factory was added:

```text
features/irrigation/lib/create-irrigation-event.ts
```

The factory creates consistent event identity and timestamps and supports injected dependencies for deterministic future tests.

Supported injected dependencies include:

```text
createId
now
```

This prevents different parts of the future backend from manually constructing incompatible irrigation events.

## 14. Due Idempotency Key

A standard idempotency key generator was added:

```text
features/irrigation/lib/create-irrigation-due-key.ts
```

Key format:

```text
irrigation:{farmId}:{scheduleId}:revision-{revision}:schedule-due
```

Example:

```text
irrigation:farm-123:schedule-abc:revision-2:schedule-due
```

The schedule revision is included so a rescheduled execution is not incorrectly treated as a duplicate of the previous schedule revision.

This key alone does not provide atomic idempotency. Real duplicate prevention will require an atomic backend/database claim operation.

---

## 15. Due Plan Resolver

A due-plan contract was added in:

```text
features/irrigation/lib/resolve-irrigation-due-plan.ts
```

The resolver combines schedule identity, controller status, route, action, duration, and idempotency key into one side-effect-free plan.

A valid plan includes:

```text
farmId
scheduleId
scheduleRevision
duration
controllerStatus
route
action
idempotencyKey
```

Legacy schedules that do not contain a reliable id or revision are rejected as invalid instead of being executed with invented identity values.

Possible invalid reasons include:

```text
missing-schedule-id
missing-schedule-revision
```

This is intentionally fail-safe because future irrigation automation will control physical hardware.

# Known Issue Found During Repository Review

Before continuing into backend idempotency work, the current committed schedule-status implementation needs one cleanup.

The repository currently defines:

```ts
export type IrrigationScheduleStatus =
  | "scheduled"
  | "past-due";
```

but `IrrigationOverview.status` is still typed as:

```ts
status: string;
```

The current Irrigation page also emits display-style values:

```text
Scheduled
Past-due
```

while the Irrigation Overview checks for:

```text
past-due
```

This casing/value mismatch can prevent the Past Due UI branch from activating correctly.

This should be fixed before continuing new automation work so the domain status remains consistently machine-readable:

```text
scheduled
past-due
```

and user-facing labels are generated only inside the presentation component.
