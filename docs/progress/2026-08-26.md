## Architecture Decisions

### Demo-data boundary

Decision:

The real AgroMind application must not use demo farms or other fake business entities as operational data.

Demo/example data may remain on the Landing Page for product demonstration only.

Real app areas should instead support purposeful empty states.

### Repository-first workflow

Decision:

At the start of each future workday, review the current repository and relevant feature files before making implementation decisions.

Reason:

This prevents stale conversation copies from overwriting newer repository code and reduces architectural inconsistencies.

### Incremental implementation

Decision:

Each task will be explained in detail, implemented as one focused step, tested, and confirmed before moving to the next task.

Reason:

This keeps AgroMind reviewable, debuggable, and production-oriented.

## Current Product Direction

AgroMind is being transitioned from an MVP/demo-style implementation toward a real user-data-driven application.

Target behavior:

- Landing Page: demo/example content allowed
- Real application: user-created/persisted data only
- Empty application state: professional onboarding/empty-state UI
- Location-dependent features: use stored farm coordinates
- Weather: use the selected farm's real coordinates
- Future AI and irrigation intelligence: use real farm data rather than hardcoded examples
